# AI Critique (200–300 words)

AI was useful for breadth, but its first draft confused a plausible testing idea with an executable test. It proposed alternative status codes, reused mutable seed records, and sometimes assumed that an authenticated token was equivalent to an administrator token. In FR-10, a state-matrix outline looked complete while several rows lacked a reliable way to create the required starting state. In FR-19, it suggested role-update tests even though the published API only exposes list and delete operations. These flaws were not random: the prompts initially emphasized coverage count more than fixture isolation, exact oracles, and postconditions.

The most important omissions were security and lifecycle interactions. AI did not initially connect a deleted user to the continued validity of an already issued JWT, nor did it reliably distinguish one root defect from many failed assertions. It also treated negative cases as if a failed assertion might be an expected result. Human review corrected this: every case now has one exact expected status, isolated setup data, schema or invariant checks, and a state/identity postcondition. Failed negative cases remain failures and are classified against ten root defects rather than inflated into sixty-three bugs.

I learned that AI collaboration works best as a sequence of constrained passes: normalize the contract, partition inputs, enumerate the state graph, map authorization and injection risks, define schemas, then audit executability. Runtime evidence must overrule confident prose. Code reading can explain an observed failure, but it cannot replace a reproducible request. Finally, provenance matters: AI-generated rows, student-added rows, corrections, and reasons for omissions must remain separately traceable. The result is slower than accepting generated output, but substantially more defensible and reusable.
