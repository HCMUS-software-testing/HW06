## 2. Nguyên Tắc Định Hướng

Các nguyên tắc này xác định cách bạn được kỳ vọng làm việc trong toàn bộ chuỗi bài tập của học phần. Hãy đọc kỹ trước khi bắt đầu, vì bài nộp của bạn sẽ được đánh giá dựa trên các nguyên tắc này.

- **Chiến lược AI-First.** Bạn bắt buộc phải áp dụng AI vào các kỹ thuật kiểm thử đã học trên lớp. Tuy nhiên, điều này không có nghĩa là chỉ đưa ra một prompt chung chung như "generate all the API test cases from the spec and run them." Thay vào đó, bạn phải hướng dẫn AI qua từng bước của kỹ thuật như đã được giảng dạy, sử dụng AI như một trợ lý có kỷ luật thay vì một hộp đen.
- **Rà soát của con người.** Mọi kết quả do AI tạo ra phải được bạn, với tư cách sinh viên, rà soát cẩn thận. Bạn hoàn toàn chịu trách nhiệm về tính đúng đắn của các kết quả này. Bạn được kỳ vọng thực hiện mọi chỉnh sửa và tinh chỉnh cần thiết - nộp nguyên kết quả thô từ AI mà không rà soát là không chấp nhận được.
- **Báo cáo Kiểm toán AI.** Toàn bộ quá trình sử dụng AI phải được ghi lại trong một nhật ký đầy đủ. Bạn được khuyến khích xây dựng Agent Skills có thể tự động thực hiện các hoạt động này cho các bài tập tương tự. Nếu không sử dụng AI, bạn vẫn phải khai báo rõ ràng điều đó.
- **Tài liệu hóa.** Toàn bộ quá trình làm việc phải được tài liệu hóa ở định dạng văn bản, chẳng hạn như Markdown.
- **Chất lượng quan trọng hơn hoàn thành.** Bài làm của bạn sẽ không chỉ được chấm dựa trên việc có hoàn thành hay không, mà còn dựa trên số lượng và chất lượng của các sản phẩm bàn giao: test cases, kiểm toán AI, Postman collection và Newman report, bug reports, thiết kế test-generator, và các liên kết tham chiếu.

## 4. Hệ Thống Được Kiểm Thử (SUT)

**SUT:** EShop - một ứng dụng demo thương mại điện tử Việt Nam được thiết kế cho thực hành kiểm thử.

**Repository:** <https://github.com/ttbhanh/eshop-sut>

Các tính năng của ứng dụng được tổ chức thành các nhóm sau:

### Pool B - Giỏ hàng và Thanh toán

- FR-07: Giỏ hàng
- FR-08: Thanh toán
- FR-09: Mã giảm giá
- FR-10: Máy trạng thái đơn hàng
- FR-11: Xem lịch sử đơn hàng (người dùng)

### Pool C - Web Admin

- FR-12: Kiểm soát truy cập
- FR-13: Bảng điều khiển
- FR-14: Quản lý danh mục (CRUD)
- FR-15: Quản lý sản phẩm (CRUD)

- FR-18: Quản lý đơn hàng (admin)

### Pool D - Ứng dụng Di động

SUT đi kèm một đặc tả API trong repository (`api_specification.md`); hãy tham khảo tài liệu này để biết các endpoint có sẵn. Đặc tả cũng định nghĩa các yêu cầu bảo mật SEC-01-SEC-07.

## 5. Lựa Chọn API

- Chọn ba (3) API, mỗi API triển khai một tính năng lần lượt từ Pool A, Pool B, và Pool C (Pool D, ứng dụng di động, không được dùng ở đây vì bài tập này nhắm đến backend API). Tham khảo đặc tả API để tìm các endpoint phía sau mỗi tính năng được chọn.
- Pool A - ví dụ: đăng nhập (FR-02) hoặc liệt kê / tìm kiếm sản phẩm (FR-05).
- Pool B - ví dụ: giỏ hàng (FR-07) hoặc thanh toán / tạo đơn hàng (FR-08, FR-10).
- Pool C - ví dụ: một thao tác sản phẩm hoặc đơn hàng của admin có thay đổi trạng thái (FR-15, FR-18).
- Như các bài tập trước, hãy đảm bảo lựa chọn của bạn không trùng với các thành viên khác trong nhóm: không hai thành viên nào được chọn cùng một bộ ba API.

## 6. Yêu Cầu

Đối với mỗi API trong ba API đã chọn, hãy hoàn thành pipeline sau. Tài liệu hóa quá trình trong báo cáo chính và đính kèm bằng chứng bắt buộc. Hãy ôn lại các bài giảng liên quan về kiểm thử API trước khi bắt đầu.

1. **Tạo bằng AI.** Cung cấp đặc tả API của SUT cho một công cụ AI và điều khiển nó - từng bước, không dùng một prompt chung chung duy nhất - để tạo test cases cho API (mục tiêu >= 35 test cases cho mỗi API). Các test cases phải bao phủ: phân hoạch miền trên mọi tham số (ví dụ: định dạng email, độ phức tạp mật khẩu, price > 0), chuyển trạng thái (FR-10: pending -> confirmed -> shipping -> delivered, cộng với quy tắc hủy), bảo mật (SEC-01-SEC-07, ví dụ: SQL injection, IDOR, leo thang vai trò), và kiểm tra schema (hình dạng response khớp chính xác với đặc tả).
2. **Kiểm toán (rà soát thủ công).** Gán nhãn mỗi test case do AI tạo là VALID / INVALID / INCOMPLETE kèm lý do, và sửa các test case không hợp lệ hoặc chưa hoàn chỉnh. Bạn hoàn toàn chịu trách nhiệm với bộ test cases cuối cùng.
3. **Mở rộng.** Thêm ít nhất năm test cases do chính bạn tạo mà AI đã bỏ sót - đặc biệt về bảo mật và chuyển trạng thái - và giải thích vì sao AI bỏ sót chúng (chất lượng prompt, giới hạn của mô hình, hoặc đặc điểm của API).
4. **Thực thi.** Chạy test cases bằng Postman + Newman (hoặc Karate / RestAssured). Mọi request phải mang header `X-Student-Id: {StudentID}` (ví dụ thông qua pre-request script). Tạo Newman / HTML report.
5. **Báo cáo lỗi.** Báo cáo mọi lỗi thật sự bạn tìm thấy - bao gồm cả lỗi AI bỏ sót - trong báo cáo Markdown và trên trang GitHub Issues của bạn, mỗi issue phải có ảnh chụp màn hình đính kèm.

Ngoài ra, các yêu cầu kỹ thuật sau áp dụng cho toàn bộ test suite:

- Sử dụng nhiều tính năng của Postman nhất có thể trong phạm vi hợp lý - ví dụ: workspaces, collections, variables, environments, data-driven runs (Collection Runner với data file), monitors, và mock servers.
- Liệt kê các tính năng Postman bạn đã sử dụng trong báo cáo. (Người dùng Karate / RestAssured cung cấp các tính năng công cụ tương đương.)
- Tích hợp vào CI/CD. Thêm API test cases của bạn vào một pipeline CI/CD cho SUT (ví dụ chạy Newman trong GitHub Actions trong repository của bạn), và viết một báo cáo CI/CD ngắn mô tả cấu hình pipeline và hai lần chạy bên dưới, kèm ảnh chụp màn hình và liên kết. Cung cấp hai commit mẫu: một commit có pipeline run cho thấy toàn bộ API test cases đều pass, và một commit có pipeline run cho thấy một test case fail.

## 7. Agent Skill

- Đối với mức Create (G9.5), thiết kế một bộ sinh test API được dẫn dắt bởi AI cho SUT: khi nhận đặc tả API, nó tự động tạo test cases.
- Cung cấp sơ đồ tự vẽ và pseudocode của thiết kế. ("Tự vẽ" nghĩa là bạn tự đưa ra các quyết định thiết kế; có thể dùng bất kỳ công cụ vẽ sơ đồ nào, nhưng bản thân sơ đồ không được AI tạo ra.)
- Bạn được khuyến khích triển khai nó như một Agent Skill có thể tái sử dụng và nộp video minh họa (liên kết YouTube) cho thấy nó sinh test cho một API.

## 8. Công Cụ Được Phép và Mức Bloom-AI

Bạn có thể sử dụng các công cụ sau, và phải khai báo chúng trong Báo cáo Kiểm toán AI:

- Bất kỳ công cụ AI nào bạn chọn (ví dụ: ChatGPT, Claude, Gemini, Copilot, Cursor).
- Postman + Newman (mặc định) hoặc Karate / RestAssured (thay thế).
- Tùy chọn: các công cụ kiểm thử LLM (Promptfoo, DeepEval, Ragas).

Mức Bloom-AI yêu cầu cho bài tập này là G9.2 (Apply), G9.3 (Analyse), G9.4 (Collaborate), và G9.5 (Create).

## 9. Báo Cáo Kiểm Toán AI (Phụ Lục Bắt Buộc)

Đính kèm Báo cáo Kiểm toán AI dưới dạng phụ lục. Sử dụng nội dung của AI Templates đã cho nếu cần.

- Nếu bạn không sử dụng AI, hãy khai báo: "I do not use any AI help in this exercise."
- Nếu bạn có sử dụng AI, hãy khai báo: "I use AI tools for the following tasks," và bao gồm các thông tin sau cho mỗi lần tương tác:
- Tên công cụ AI
- Ngày và giờ
- Prompt của bạn
- Kết quả đầu ra của AI

Để đơn giản hóa quá trình này, bạn được khuyến khích tạo một skill hoặc rule tự động trích xuất các thông tin trên sau một phiên làm việc với AI.

## 11. Ràng Buộc Chống Gian Lận Bằng AI

Bài tập này dựa trên bằng chứng thực thi thật và có thể quy trách nhiệm. Những nội dung sau không được AI tạo ra hoặc bịa đặt, và trợ giảng sẽ kiểm tra khi chấm:

- Header `X-Student-Id: {StudentID}`, được chứng minh bằng ảnh chụp màn hình console từ pre-request script của bạn.
- Kết quả chạy Newman, trong đó hostname khớp với deployment của bạn (`localhost` / `127.0.0.1` được chấp nhận).
- Sơ đồ AI test-generator, phải là sơ đồ tự vẽ - do bạn thiết kế, không được AI tạo trực tiếp.

## 14. Quy Định Nộp Bài

- Định dạng tên file: `<StudentID>_HW06_AI_API_<SelfAssessedGrade>.zip`
- `SelfAssessedGrade`: số gồm 3 chữ số trong khoảng [000, 100].
- Ví dụ: `25127001_HW06_AI_API_090.zip`

Nội dung bắt buộc của file `.zip`:

- Báo cáo chính (Markdown + PDF), bao gồm báo cáo kiểm thử API và kiểm toán AI của bạn.
- Liên kết public GitHub repository (collections, scripts, và reports).
- Postman collection (`.json`) và Newman report (HTML), cùng danh sách các tính năng Postman bạn đã sử dụng.
- Báo cáo CI/CD ngắn: cấu hình pipeline và hai pipeline run mẫu (một run pass toàn bộ, một run có một test case fail), kèm ảnh chụp màn hình và liên kết.
- Excel test cases và test summary.
- Sơ đồ và pseudocode của AI test-generator (PNG / Mermaid + `.md` / `.py`).
- Tùy chọn: đặc tả API được chuyển đổi sang OpenAPI (`.yaml` / `.json`); nếu do AI tạo, cũng phải kiểm toán.
- Bug report, kèm ảnh chụp màn hình các bug trên trang GitHub Issues.
- AI Critique và AI Audit Report (Markdown + PDF).
- Git commit log (file văn bản).
- Một file `README.md` chứa bảng tự đánh giá (bên dưới) và báo cáo tóm tắt kiểm thử: số lượng API; số test cases được tạo, được thêm, được thực thi, pass, fail; và số lượng bug.
- Bất kỳ tài liệu hỗ trợ nào khác.

Nộp lên Moodle. Hạn nộp xem tại liên kết nộp bài.
